# Промпты по фазам

Схема работы на каждой фазе:
1. **zcode** получает промпт фазы и делает работу в отдельной ветке `phase-N-...`.
2. **Claude Code (Opus 5.5)** получает общий промпт ревью + чек-лист этой фазы.
3. Замечания ревью отправляются обратно в zcode промптом «Исправления».
4. Merge в `main` только после повторного ревью без блокирующих замечаний.

Рекомендация по моделям zcode: **GLM 5.3 max** для фаз 0, 3, 4, 5, 6 (математика, бэктест, LLM-логика),
**GLM 5.3 flash max** для фаз 1, 2, 7, 8, 9, 10 (каркас, загрузчики, UI, деплой).

## Общая шапка (вставлять в начало каждого промпта для zcode)

```

При противоречии docs/decisions.md имеет приоритет над SPEC.md (это зафиксированные отступления).

не реализуя отступление молча. Осознанные отступления записывай в docs/decisions.md (дата, решение, причина).

Правила:
- Работай в ветке, указанной в задаче. Маленькие осмысленные коммиты на английском.
- Не выходи за рамки фазы. Не реализуй функции будущих фаз.

- Никаких секретов в коде и коммитах: только .env (в .gitignore) и .env.example.

  используй отдельный файл базы через DATABASE_URL. Перед любой миграцией или массовым изменением
  данных делай копию: cp valuebet.db backups/valuebet-$(date +%Y%m%d-%H%M).db (backups/ в .gitignore).
- Внешние HTTP-запросы в тестах замоканы (respx/vcrpy с записанными фикстурами).
- В конце напиши отчёт: что сделано, что не сделано, какие допущения принял, как проверить вручную.
```

```

Код здесь только исследовательский (scripts/recon/), качество production не требуется.

Проверь и задокументируй в docs/data-sources.md:
1. football-data.co.uk: какие сезоны и колонки есть для топ-5 лиг (результаты, закрывающие O/U 2.5,
   какие букмекеры).
2. Understat через soccerdata (или альтернативу): можно ли стабильно получить xG по матчам топ-5 лиг
   за 5 сезонов и текущий; скорость; нужен ли кэш.
3. API-Football бесплатный тариф: точный дневной лимит, доступен ли ТЕКУЩИЙ сезон на бесплатном
   плане (на некоторых планах доступ к сезонам ограничен — проверь фактически), есть ли эндпоинты
   fixtures, lineups, injuries, результаты для топ-5 и ЛЧ.
4. Odds-API (минимум 2 кандидата, например The Odds API и odds из API-Football): какие рынки
   реально отдаются для футбола на бесплатном тарифе — тоталы с какими линиями, есть ли точный счёт,
   «обе забьют»; какие букмекеры; лимит запросов в месяц; хватит ли его на опрос матчей топ-5 + ЛЧ
   на 72 часа вперёд раз в 6 часов. Посчитай бюджет запросов.
5. Поисковые API с бесплатной квотой (минимум 2 кандидата, например Tavily): лимит, качество
   выдачи на запрос «<команда> injury news team news» на 3 реальных ближайших матчах.
6. Gemini API: какие модели доступны по ключу из .env, проверь structured output (JSON schema).

Для каждого источника: работает / не работает, лимиты (цифры, проверенные фактически), риски,
рекомендация. В конце — итоговая таблица выбора и пересчитанный бюджет квот.
Ключи бери из .env (сделай .env.example со списком нужных переменных).
```

**Чек-лист ревью фазы 0:** лимиты подтверждены реальными запросами, а не взяты из памяти модели;
бюджет квот посчитан арифметически; проверен доступ к текущему сезону в API-Football;
явно сказано, есть ли точный счёт в каком-либо бесплатном odds-API.

## Фаза 3 — Модель
Ветка: `phase-3-model`

```
[Общая шапка]

Задача: модель по разделу 4 SPEC.md и вывод рынков из раздела 1.
- Dixon-Coles для каждой лиги: атака/оборона команд, домашнее преимущество лиги, rho для низких
  счетов, ограничение идентифицируемости (сумма атак = 0 или аналог).
- Затухание по времени exp(-xi * days).
- Квази-пуассоновское правдоподобие на целевой величине w*goals + (1-w)*xG.
- Оптимизация через scipy.optimize (L-BFGS-B), разумные начальные значения, проверка сходимости.
- Интерфейс: fit(matches_before: date) -> FittedModel; FittedModel.score_matrix(home, away) -> 11x11
  numpy-массив, сумма = 1 (хвост перенормирован). Обучение принимает ТОЛЬКО матчи до даты прогноза.
- core/model/markets.py — чистые функции от матрицы: exact_score(h,a), multiscore_set(scores),
  goals_range(lo,hi), total_over(line), total_under(line), btts(yes/no).
- Обработка промоутированных команд без истории (априорные значения, например среднее слабых
  команд лиги; описать в docs/decisions.md).

Тесты: свойства рынков (over+under=1 для полулиний, сумма матрицы=1, btts yes+no=1), восстановление
известных параметров на синтетических данных, сгенерированных из модели с заданными параметрами,
поведение rho на счетах 0:0/1:0/0:1/1:1.
```

**Чек-лист ревью фазы 3 (самый важный):** проверить математику tau-коррекции Dixon-Coles по
оригинальной статье; отсутствие утечки будущего в fit; корректность квази-правдоподобия при
нецелых значениях; тест на синтетике действительно восстанавливает параметры; поведение при
отсутствии xG у части матчей.

## Фаза 5 — Value-движок, флаги, ручной ввод
Ветка: `phase-5-value`

```
[Общая шапка]

Задача: разделы 4, 5 и 6 SPEC.md v2 (без LLM — она в фазе 6).
- Справедливая рыночная матрица точного счёта (core/value/market_matrix.py или core/model/):
  построение из рыночных предматчевых O/U 2.5 и 1X2 без маржи (Pinnacle, при отсутствии — consensus)
  с поправкой на высокие ничьи kappa_high = 0.20 (2:2, 3:3).
- core/value/engine.py:
  - Базовый расчёт: вероятности берутся из справедливой рыночной матрицы.
  - Резерв (fallback): если рыночные коэффициенты O/U или 1X2 отсутствуют/неполны, вероятности берутся
    из модели Dixon-Coles (p_model). Обучение резервной модели строго на матчах ДО даты прогноза (result_lag 2ч).
  - Отбор кандидатов (предфильтр) на покупку Pinnacle correct_score и ручной ввод цен Fortuna:
    (1) наличие сетки точного счёта Fortuna (пользователь отмечает); (2) масса высоких ничьих
    в справедливой рыночной матрице (где работает kappa_high); (3) ротация по лигам;
    (4) бюджетный лимит (до 10 матчей в неделю). Расхождение модели с рынком служит ТОЛЬКО
    сигналом/флагом «проверить составы/данные», БЕЗ повышения приоритета ставки (у модели alpha=0).
  - Бенчмарк валидации (B6.3): справедливая матрица из де-маржинализованной сетки Pinnacle correct_score
    (The Odds API) для матчей с доступными данными.
  - Расчёт edge: edge = p_fair_market * odds_fortuna - 1 (или p_model * odds_fortuna - 1 при fallback).
  - Применение порогов: точный счёт (edge >= 12%, p >= 4%, odds <= 21), мультисчёт (edge >= 8%).
  - Тоталы O/U и BTTS — справочно (reference-only); рынок 1X2 — строго входной (input-only, рекомендаций нет).
  - Возвращает список кандидатов: рынок, линия/исход, odds_fortuna, bookmaker="fortuna", p_fair, p_model,
    edge, flags, kelly_quarter_capped.
- Ключевые игроки: расчёт по составам (>=70% стартов из последних 8, параметры в конфиге).
- Флаги риска по API-Football-доступности: ⚠️ и порог x 1.5 при отсутствии ключевого игрока;
  исключение при >=2 ключевых отсутствующих. Интерфейс должен принимать дополнительные отсутствия
  из других источников (фаза 6) и флаг «противоречие источников».
- core/value/manual_parser.py: парсер свободного текста ручных коэффициентов Fortuna на сетку
  точного счёта и мультисчёт («2:1 @ 8.5», «2-1 8.5», «1:1, 2:1, 2:2 @ 3.4» как мультисчёт-набор,
  «2-4 гола @ 1.80», «1:0, 2:0, 3:0 @ 4.2»); десятичные через точку и запятую;
  непонятные строки возвращаются как ошибки с указанием строки, а не игнорируются.
- Сохранение рекомендаций в recommendations (variant=base, bookmaker="fortuna").
Тесты: калибровка справедливой матрицы, fallback на Dixon-Coles, де-маржинализация O/U и 1X2,
пороги и флаги, много случаев для парсера котировок Fortuna (включая синтаксический мусор).
```

**Чек-лист ревью фазы 5:** базовая матрица строится строго из де-маржинализованного рынка (O/U 2.5 + 1X2)
с kappa_high = 0.20 (2:2, 3:3, ...); бенчмарк Pinnacle correct_score поддержан; модель Dixon-Coles используется
как fallback и детектор аномалий (без повышения приоритета ставки); отбор кандидатов учитывает сетку Fortuna,
массу ничьих, ротацию и лимит <= 10/нед; edge считается против коэффициентов Fortuna; тоталы и 1X2 не попадают
в рекомендации; Келли с потолком; парсер надёжно обрабатывает ручной ввод сетки Fortuna; повторный прогон не плодит
дубли рекомендаций.

## Фаза 6 — Новости и LLM
Ветка: `phase-6-news-llm`

```
[Общая шапка]

Задача: раздел 6 SPEC.md v2, LLM-часть, и абстракция провайдера.
- core/llm: интерфейс LLMProvider (generate_structured(schema, prompt), generate_text(prompt)),
  реализация Gemini. Модели берутся из конфига: extraction_model (быстрая), reasoning_model (сильная).
  Ретраи, таймауты, лог каждого вызова в llm_calls (промпт, ответ, модель, токены, стоимость если есть).
- core/news: поисковый клиент (Tavily/аналог) с учётом квоты; запуск только для матчей-кандидатов из

  T-24ч и T-3ч (дедупликация: не искать повторно, если поиск по матчу уже был в этом окне).
- Извлечение: строгий JSON по схеме из SPEC (player, team, status, source_url, quote_summary).
  Валидация pydantic; невалидный ответ → один повтор, затем пропуск с логом. Сопоставление имён игроков
  с данными API-Football (нечёткое сравнение), несопоставленные — в лог.
- Слияние с данными API-Football → передача в флаги value-движка (включая «противоречие источников»).
- Обоснование: reasoning_model пишет 2–3 предложения на русском по ЦИФРАМ, которые ей передали
  (p_fair, p_model, odds_fortuna, edge, форма, отсутствия). Промпт явно запрещает придумывать новые числа;
  проверка постфактум: числа в тексте должны совпадать с переданными, иначе — шаблонное обоснование.
- Теневой режим: reasoning_model возвращает JSON с множителями атаки/обороны в диапазоне [0.8, 1.2]
  и кратким объяснением; модель пересчитывает матрицу; рекомендации сохраняются как
  variant=shadow_llm. Пользователю нигде не показываются, кроме страницы сравнения в дашборде.
Тесты с замоканным провайдером: валидация схемы, повтор, проверка чисел в обосновании,
ограничение множителей, дедупликация поиска.
```

**Чек-лист ревью фазы 6:** в основном контуре LLM ни на что числовое не влияет (проследить поток
данных); prompt injection из текста новостей не может изменить формат/поведение (новости передаются
как данные, результат строго валидируется схемой); квота поиска соблюдается; shadow-рекомендации
не протекают в выдачу пользователю.

## Фаза 7 — Трекинг, расчёт, планировщик
Ветка: `phase-7-tracking`

```
[Общая шапка]

Задача: раздел 7 SPEC.md v2 + core/scheduler.
- Расчёт результатов рекомендаций по итоговому счёту (точный счёт, мультисчёт).
- Арбитр качества (review B2): CLV (Closing Line Value):
  CLV_fair = odds_fortuna (введённая пользователем при рекомендации) × p_fair − 1,
  где p_fair — вероятность исхода по справедливой рыночной матрице, построенной из ПОСЛЕДНЕГО
  снимка totals+h2h строго ДО начала матча (не после). Вторично, для кандидатов с купленным
  рынком Pinnacle correct_score — CLV_pinnacle против последнего предматчевого снимка Pinnacle без маржи.
  У каждого значения сохраняется clv_source ("fair_market_matrix" / "pinnacle_correct_score").
  Реализованный ROI приводится исключительно справочно (на коэффициенте ~9 для CI ±5% нужно ~12 000 ставок).
- Метрики: CLV (основной арбитр), ROI (справочно, включая отрицательный), hit rate, средний edge,

- APScheduler:
  - Ежедневное обновление истории и xG;

  - Событие «новый value» в таблицу notifications (для Hermes).
```
