## Changelog v2 (Итоги фаз 4 и 4b, ревизия архитектуры)

По результатам бэктестов фазы 4 и 4b (см. `reports/backtest/SUMMARY.md` и `SUMMARY_4b.md`) зафиксирован ключевой пивот архитектуры:
- **Пивот от модели к рыночной матрице**: статистическая модель Dixon-Coles не имеет преимущества перед рынком ни на тоталах (ROI отрицательный / нейтральный по CLV: 47.4% к нам, средний сдвиг 0.00 п.п.), ни на точном счёте. Матрица точного счёта, построенная целиком из рыночных предматчевых коэффициентов (O/U 2.5 + 1X2 без маржи) с поправкой на высокие ничьи ($\kappa_{\text{high}} = 0.20$), превосходит гибрид с модельными долями голов на −0.016 по log loss (CI95 [−0.021, −0.011]), и превосходит чистую модель Dixon-Coles на −0.0218 (2.8894 — рыночная матрица с $\kappa_{\text{high}}$ против 2.9112 — чистая модель на валидации). Кросс-фит веса модели $\alpha$ в долях голов даёт строго $\alpha = 0.0000$ (OOS дельта +0.0000). Не следует путать это с весом смеси логитов на тоталах O/U (0.14–0.25), где модель на валидации вне выборки также не лучше рынка.
- **Новая роль модели**: Dixon-Coles переходит в статус резервного источника (fallback при отсутствии полных рыночных линий) и детектора аномалий. Расхождение между моделью и рынком служит сигналом проверки («проверить составы/данные»), но не увеличивает приоритет ставки.
- **Букмекер и ставки**: пользователь ставит **исключительно у букмекера Fortuna** (польская лицензия). Все остальные букмекеры (Pinnacle, биржи, консенсус) используются исключительно как справочный ориентир справедливой цены.
- **Рекомендации vs Справочно**: рекомендации формируются **только** на рынки точного счёта и мультисчёта (где у букмекера высокая маржа и частые ручные перекосы). Тоталы O/U и BTTS — строго справочные (reference-only). Рынок 1X2 — строго входной (input-only), бот на него никогда не рекомендует ставить.
- **Квоты и арбитр**: опрос The Odds API переведён на уровень спорта (`markets=totals,h2h`), T-48 выключен, T-24 и T-3 (по слотам) включены, бюджет ~392–393 кредитов/30д (жесткий стоп 450). Арбитр качества для фазы 7 — предматчевый CLV (Closing Line Value) против справедливой матрицы из последнего снимка `totals+h2h` строго до матча (`clv_source="fair_market_matrix"`), а также вторично против де-маржинализованного Pinnacle `correct_score` (`clv_source="pinnacle_correct_score"`).

## 1. Цель

Сервис ищет **value bets** на рынках футбольных матчей у букмекера **Fortuna** (польская лицензия).
Value — ситуация, где коэффициент Fortuna на точный счёт или мультисчёт выше вероятности, рассчитанной по справедливой рыночной матрице: `edge = p_fair_market * odds_fortuna - 1 > порог`.
При отсутствии полных рыночных линий резервным источником вероятностей служит статистическая модель: `edge = p_model * odds_fortuna - 1`.

Бот **не** угадывает победителя, **не** ставит на рынок 1X2 и **не** ставит автоматически.
Он рекомендует, логирует и честно считает свою статистику.

### Рынки
- **Точный счёт** (одна ячейка матрицы счетов) — **рекомендация**.
- **Мультисчёт** в двух формах: набор счетов (`{1:0, 2:0, 2:1}`) и диапазон суммы голов (`2–4 гола`) — **рекомендация**.
- **Тоталы** больше/меньше: 0.5, 1.5, 2.5, 3.5, 4.5 (матч целиком) — **справочно** (reference-only, фаза 4b B4).
- **Обе забьют** (BTTS, да/нет) — **справочно** (reference-only).
- **1X2** (исход) — **строго входной рынок** (input-only, фаза 4b B6). Используется для калибровки рыночной матрицы точного счёта, рекомендаций по нему не выдаётся.

### Покрытие
- Топ-5 лиг: Premier League, La Liga, Serie A, Bundesliga, Ligue 1.
- Лига чемпионов: рынки точного счёта и мультисчёта оцениваются по справедливой рыночной матрице (рыночные котировки O/U 2.5 и 1X2 присутствуют в The Odds API), отдельный флаг `experimental` (фаза 11); тоталы — справочно.

## 2. Ключевой принцип

**Все вероятности определяются справедливым рыночным расчётом или статистической моделью. LLM никогда не задаёт числа в основном контуре.**
LLM только: (а) извлекает факты из новостей в JSON, (б) пишет текстовое обоснование,
(в) в теневом режиме предлагает поправку, которая логируется, но пользователю не показывается.

### Бюджет кредитов The Odds API (30 дней)

Фактические замеры числа вызовов за 28 дней без пауз между турами (`reports/recon/odds_budget.json`, политика `d_snapshots` по 6 видам спорта: топ-5 лиг + UCL):
- T-48: 64 вызова / 28д (68.57 / 30д);
- T-24: 68 вызовов / 28д (72.86 / 30д);
- T-3 по слотам начала матчей: 91 вызов / 28д (97.50 / 30д);
- T-3 по дням: 68 вызовов / 28д (72.86 / 30д);
- Всего вызовов на 1 рынок: 223 / 28д = 238.93 ≈ 239 / 30д.

Стоимость вызова TOA линейна: `markets × regions` (в регионе `eu` при `markets=totals,h2h` стоимость составляет 2 кредита за вызов).
Сценарий с включением `totals+h2h` на всех трёх тирах (T-48, T-24, T-3) даёт $(64 + 68 + 91) \times 2 \times 30/28 = 477.86$ кредитов, плюс опрос результатов UCL (`/scores`, 8.57 кр./30д) $\to$ **486.43 ≈ 487 кредитов / 30д**, что превышает аварийный стоп 450 кредитов даже без покупки единичных рынков кандидатов.

**Принятая схема по умолчанию** (расчёт зафиксирован в артефакте `reports/recon/odds_budget_30d.json` через скрипт `scripts/calc_odds_budget.py`):
- **T-48**: выключен (0 вызовов);
- **T-24**: включен с `markets=totals,h2h` (2 кредита) $\to$ 145.71 кр./30д;
- **T-3 (по слотам начала матчей)**: включен с `markets=totals,h2h` (2 кредита) $\to$ 195.00 кр./30д;
- **Результаты UCL (`/scores`)**: 8.57 кр./30д (≈ 9 кр.);
- **Pinnacle `correct_score`** (точечно по кандидатам): $\le 10$ матчей в неделю $\to 10 \times 30/7 = 42.86$ кр./30д (≈ 43 кр.);
- **Итого по умолчанию**: **392.14 ≈ 393 кредита / 30д** (запас до стопа 450 — 57.86 кредитов, до квоты 500 — 107.86 кредитов).

Вариации объёма кандидатов Pinnacle `correct_score`:
- 0 матчей/нед: 349.29 кр./30д (запас 100.71);
- 5 матчей/нед: 370.71 кр./30д (запас 79.29);
- 10 матчей/нед (номинал): 392.14 кр./30д (запас 57.86);
- 15 матчей/нед: 413.57 кр./30д (запас 36.43).

**Лестница деградации квот (при приближении к лимиту 450 или срабатывании пейсинга)**:
1. `cap_correct_score_5_week`: ограничение покупок Pinnacle `correct_score` до 5 матчей в неделю $\to$ **370.71 ≈ 371 кр./30д**;
2. `disable_t3_h2h`: выключение `h2h` на тире T-3 (на T-3 запрашиваются только тоталы за 1 кредит, доля голов берётся из снимка T-24) $\to$ **273.21 ≈ 273 кр./30д**;
3. `t3_slot_to_day`: переключение T-3 со слотов на дни матчей (68 вызовов вместо 91, только тоталы за 1 кредит) $\to$ **248.57 ≈ 249 кр./30д**;
4. `t3_never_disabled`: тир T-3 **не выключается никогда** (сохраняется минимальный пол сбора линии). Везде используется T-3 (решение фазы 0), не T-2.

## 4. Справедливая рыночная матрица и модель

### Базовый контур (Справедливая рыночная матрица)
- Базовая матрица вероятностей точного счёта 0..10 × 0..10 строится целиком из де-маржинализованных предматчевых рыночных коэффициентов (O/U 2.5 + 1X2; Pinnacle, при отсутствии — consensus).
- $\lambda_{\text{total}}$ выводится точно из де-маржинализованного O/U 2.5; доля голов хозяев подбирается методом наименьших квадратов (МНК) по де-маржинализованному 1X2; параметр $\rho$ строго фиксируется $\rho = 0$. Обоснование по закоммиченным поматчевым массивам валидации ($n=3504$, 76 недель): оценка $\rho$ из рыночной вероятности ничьей против $\rho = 0$ даёт выигрыш всего $-0.0013$ $[-0.0032, +0.0006]$, что статистически неотличимо от нуля. По правилу «неотличимо — бери проще» принят единственный вариант $\rho = 0$. Модельный $\rho$ не используется (вклад $-0.0006$ $[-0.0026, +0.0014]$ также неотличим от нуля). Требование точно воспроизвести оба рынка одновременно снято, так как система переопределена (2 параметра на 3 уравнения).
- Коррекция на высокие ничьи: поправка $\kappa_{\text{high}} = 0.20$ применяется ко всей диагонали от 2:2 и выше (2:2, 3:3, 4:4, ...) для компенсации структурного занижения ничьих в независимом пуассоновском хвосте.
- Все рынки рекомендаций (точный счёт, мультисчёт) выводятся из матрицы чистыми функциями.

### Резервный контур и детектор аномалий (Dixon-Coles)
- **Dixon-Coles** отдельно для каждой лиги: параметры атаки и обороны для каждой команды, преимущество своего поля, затухание по времени $\exp(-\xi \cdot \text{дни})$, смесь голов и xG $w \cdot \text{goals} + (1 - w) \cdot \text{xG}$.
- **Обучение без утечек**: обучение и калибровка резервной модели Dixon-Coles проводятся строго на матчах, завершившихся ДО даты прогноза, с учётом `result_lag` (2 часа после окончания матча), исключая любую утечку будущих данных.
- **Fallback**: используется, если предматчевые рыночные котировки недоступны или неполны.
- **Сигнал аномалии**: расхождение между моделью Dixon-Coles и рыночной матрицей служит ТОЛЬКО флагом «проверить составы/данные», не повышая приоритет ставки (у модели $\alpha=0$).
- **Бенчмарк валидации (decisions B6.3)**: для матчей с купленной сеткой точного счёта Pinnacle (через TOA) рыночная матрица проверяется против де-маржинализованной сетки Pinnacle correct_score.

## 5. Отбор value

- `edge = p_fair_market * odds_fortuna - 1` (при отсутствии рынка — `p_model * odds_fortuna - 1`).
- Пороги по рынкам (в конфиге, стартовые значения):
  - мультисчёт: edge ≥ 8%;
  - точный счёт: edge ≥ 12%, `p_fair_market ≥ 4%`, коэффициент ≤ 21;
  - тоталы и 1X2: рекомендации не выдаются (справочно).
- **Критерии предфильтра кандидатов** (на покупку сетки Pinnacle correct_score и ручной ввод цен Fortuna):
  1. Наличие сетки точного счёта Fortuna (пользователь отмечает/подтверждает);
  2. Масса высоких ничьих в справедливой рыночной матрице (зона действия поправки $\kappa_{\text{high}}$);
  3. Ротация по лигам;
  4. Бюджетный лимит (до 10 матчей в неделю).
  - Расхождение модели Dixon-Coles с рынком служит **ТОЛЬКО флагом проверки**, без повышения приоритета ставки.
- Ручной ввод: парсер свободного текста вида `2:1 @ 8.5, 1:1 @ 6.0, 2-4 гола @ 1.80, 1:0, 2:0, 2:1 @ 3.4`.

## 6. Составы и флаг риска ⚠️

- **Ключевой игрок** — входил в старт в ≥ 70% из последних 8 матчей команды (параметры в конфиге).
- Источники отсутствий: API-Football (травмы/дисквалификации) + LLM-извлечение из новостей.
- LLM возвращает строгий JSON: `[{player, team, status: out|doubtful|suspended, source_url, quote_summary}]`.
- Правила флага:
  - отсутствует ключевой игрок или источники противоречат друг другу → ⚠️, порог edge × 1.5;
  - отсутствуют ≥ 2 ключевых игрока одной команды → ставка исключается.
- **Теневой режим**: LLM предлагает множители к атаке/обороне; модель пересчитывается с ними; результат логируется как `variant=shadow_llm`, пользователю не показывается.
- Поиск новостей запускается только для кандидатов в value: за T-24ч и T-3ч до матча.

## 7. Ставки и трекинг

- Для оценки качества каждая рекомендация считается ставкой в **1 условную единицу** (flat).
- Дополнительно показывается размер по ¼ Келли с потолком 2% банка — только как информация.
- Логируется всё: время, рынок, коэффициент Fortuna в момент рекомендации, `p_fair_market`, `p_model`, edge, флаги, вариант (`base` / `shadow_llm`), закрывающий коэффициент, результат, а также метрика CLV с указанием источника `clv_source`.
- Расчёт результатов автоматически по итоговому счёту из API-Football.
- **Арбитр качества (Phase 7)**: **CLV** (Closing Line Value):
  $$\text{CLV}_{\text{fair}} = \text{odds}_{\text{fortuna}} \times p_{\text{fair}} - 1$$
  где:
  - $\text{odds}_{\text{fortuna}}$ — коэффициент букмекера Fortuna, введённый пользователем в момент формирования рекомендации;
  - $p_{\text{fair}}$ — вероятность исхода по справедливой рыночной матрице, построенной из **ПОСЛЕДНЕГО снимка `totals+h2h` строго ДО начала матча** (не после начала матча!);
  - Вторично, для матчей-кандидатов с купленным рынком `correct_score` Pinnacle: $\text{CLV}_{\text{pinnacle}} = \text{odds}_{\text{fortuna}} \times p_{\text{pinnacle}} - 1$ против последнего предматчевого снимка Pinnacle `correct_score` без маржи (де-маржинализованного);
  - Для каждого сохранённого значения обязательно фиксируется `clv_source` (`fair_market_matrix` или `pinnacle_correct_score`).
- **Реализованный ROI приводится исключительно справочно**: на коэффициентах точного счёта / мультисчёта (в среднем $\approx 9$) доверительный интервал $\pm 5\%$ по ROI требует около **12 000 ставок**. Поэтому статистически состоятельным арбитром качества является CLV против закрывающего рынка.
- Метрики: CLV (основной арбитр), ROI (справочно), hit rate, средний edge, калибровка (Brier, reliability), сравнение `base` и `shadow_llm`, разбивка по рынкам и лигам.

## 8. Бэктест (итоги фаз 4 и 4b)

- Walk-forward по прошлым сезонам (2021–2024): модель переобучается строго на прошлых данных.
- Результат на O/U 2.5: Dixon-Coles не превосходит закрывающий рынок (CLV нейтрален: 47.4% смещений к нам, средний сдвиг 0.00 п.п.; ROI отрицательный с поправкой на маржу). Тоталы переведены в справочный режим.
- Результат на точном счёте: рыночная матрица (O/U 2.5 + 1X2 + $\kappa_{\text{high}}=0.20$) превосходит гибрид с долями модели на −0.016 по log loss (CI95 [−0.021, −0.011]) и превосходит чистую модель Dixon-Coles на −0.0218 (2.8894 против 2.9112 на валидации). Логит-смесь модели с рынком даёт вес модели $\alpha = 0.0000$ на валидации вне выборки.
- Тестовый период (с 2025-07-01) после фазы 4b исчерпан. Все дальнейшие бэктесты и калибровки проводятся строго на валидационной выборке. Оценка боевого качества контура проводится исключительно в режиме прямого форвардного трекинга (forward testing в фазе 7).

## 9. Архитектура

```
core (Python-пакет)
 ├─ ingest/      загрузчики данных, кэш, учёт квот
 ├─ model/       Dixon-Coles, рыночная матрица счетов, рынки
 ├─ value/       edge против Fortuna, пороги, флаги, парсер ручного ввода, детектор аномалий
 ├─ news/        поиск, LLM-извлечение, обоснования, теневая поправка
 ├─ llm/         абстракция провайдера (Gemini первым)
 ├─ tracking/    логирование, расчёт результатов, CLV-метрики
 ├─ backtest/    валидация, бутстреп, блокировка тестового периода
 └─ scheduler/   APScheduler: обновление данных, снимки odds, новости, расчёт
api/        FastAPI поверх core
mcp/        MCP-сервер для Hermes поверх того же core
dashboard/  Streamlit (ходит в api, не в базу напрямую)
```

- Хранилище: **SQLite** + SQLAlchemy + Alembic.
- Конфиг: `config.yaml` (лиги, пороги, параметры модели, модели LLM); секреты в `.env`.
- Python 3.12, менеджер `uv`, `ruff`, `mypy` (строгий режим для `core/model`, `core/value`, `core/backtest`), `pytest`.
- Развёртывание: Docker Compose на сервере Hermes (Oracle Cloud, ARM64).

### Клиенты
- **Hermes** через MCP-инструменты: `get_value_bets(days, leagues)`, `evaluate_manual_odds(match, text)`, `get_match_analysis(match)`, `get_performance(period)`.
  - Запасной путь при недоступности MCP: REST-скилл Hermes Agent, вызывающий эндпоинты FastAPI.
  - Уведомления: периодическая доставка уведомлений о новых value через планировщик Hermes (cron-опрос `GET /notifications?since=`).
- **Streamlit-дашборд**:
  - Страницы: «Value сейчас» (текущие кандидаты с флагами), «Ручной ввод» (котировки Fortuna), «История и аналитика» (ROI/CLV, калибровка), «Base vs Shadow» (сравнительный анализ базовой матрицы и теневой LLM-поправки `variant=shadow_llm`).
